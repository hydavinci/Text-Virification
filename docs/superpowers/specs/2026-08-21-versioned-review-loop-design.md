# 版本化审阅闭环设计

## 1. 背景与目标

当前项目的异步任务、持久化、并发控制、导出快照、错误恢复和可访问性强于参考项目
`C:\Work\translation-pre-checker-all`，但缺少参考项目已经投入使用的若干审阅能力。

本设计是完整功能迁移的第一个子项目，目标是在现有 FastAPI、PostgreSQL、Redis、Celery、SSE
和 Vue 工作台内原生实现：

- 按段落编辑全文并重新检查；
- 原文、修改后、字符级差异三种视图；
- 多候选建议和自定义修改；
- 单项撤销、10 秒批量快捷撤销和长期操作历史；
- 正则、区分大小写、替换当前、全部替换和键盘导航；
- 可复现且与导出严格一致的修改预览；
- 历史版本可追溯和失败可恢复。

参考项目只作为生产行为基线和规则来源，不复用其前端状态管理或 Flask 接口。后续的规则与配置、
格式与导出、连续性与智能复核分别设计和实施，不属于本子项目。

## 2. 设计原则

1. 成功分析过的文档版本不可变，编辑和重新检查必须生成新版本。
2. 问题、建议和决定只属于产生它们的文档版本，不跨版本迁移。
3. 修改后视图和修改版导出使用同一个派生内容服务。
4. 用户输入、草稿和已成功版本不得因分析失败或网络中断而丢失。
5. 并发冲突必须显式返回，禁止后写静默覆盖。
6. 继续使用现有 C2 单屏工作台，不为功能迁移恢复参考项目的拥挤布局。

## 3. 范围

### 3.1 包含

- 文档版本与服务端编辑草稿；
- 版本历史和当前版本切换；
- 多候选建议、自定义替换文本和决定扩展；
- 可逆的单项与批量操作；
- 三种文档视图和字符级 LCS 差异；
- 编辑模式中的增强查找替换；
- 重新分析任务、SSE 进度和原子切版；
- 预览与导出共用的派生内容接口；
- 桌面、平板和手机端交互与可访问性测试。

### 3.2 不包含

- 25 类规则对齐、检查开关、自定义术语和禁用词；
- DOC、RTF、Markdown、CSV 输入；
- Word 修订、PDF 标注和 RTF/文本修订导出；
- 跨浏览器会话恢复、LLM 语义复核和词典热加载；
- 多用户权限、任务历史中心或多任务标签页；
- 富文本所见即所得排版编辑。

上述能力由后续三个子项目补齐。本设计不得阻碍它们接入。

## 4. 领域模型

### 4.1 DocumentVersion

每次成功或正在进行的分析对应一个独立版本，至少包含：

- `id`、`job_id`、`parent_version_id`；
- 单任务内单调递增的 `revision_number`；
- `status`：`queued`、`analyzing`、`succeeded`、`failed`；
- `source_kind`、规范化内容哈希和段落快照；
- `created_reason`：初始上传或编辑后重新检查；
- 创建、开始、完成时间和失败原因。

任务记录持有 `active_version_id`，只能指向 `succeeded` 版本。旧成功版本保持只读。

### 4.2 ParagraphSnapshot

一个版本由有序段落快照组成。每个段落具有稳定的版本内 ID、顺序、文本和原文件位置映射。
问题范围使用段落 ID 加段落内字符偏移表示。编辑产生的新版本创建新快照，不假设旧偏移仍然有效。

### 4.3 EditDraft

草稿基于一个成功版本创建，保存有序段落文本、草稿修订号、基版本 ID、内容哈希和更新时间。
草稿服务端持久化。更新必须携带当前修订号；修订号过期时返回冲突，不覆盖服务器内容。

同一任务可以保留失败后的草稿，但同一基版本只能有一个活动草稿。重新分析成功后将该草稿标记为已消费。

### 4.4 IssueSuggestion

每个问题可拥有多个有序候选，至少包含：

- 候选文本和显示顺序；
- 来源：规则、词典、LLM 或人工；
- 可选说明和置信信息；
- 是否为系统首选。

本子项目先兼容现有单建议数据，将其映射为第一个候选；后续规则和 LLM 子项目可追加候选。

### 4.5 Decision

决定绑定文档版本和问题，包含：

- 状态：未处理、接受或忽略；
- 最终替换文本；
- 候选来源 ID；自定义修改时为空；
- 乐观锁版本；
- 最近一次操作批次 ID。

接受决定必须保存最终替换文本。修改后视图和导出不能在运行时重新选择系统首选。

### 4.6 ReviewOperationBatch

每次单项或批量决定写入一个操作批次。批次记录操作类型、时间、影响数量，以及每个决定修改前后的完整值。
撤销通过新事务恢复修改前值并记录反向操作，不删除历史。

批量操作完成后提供 10 秒快捷撤销；快捷入口消失后，用户仍可在操作历史中整批撤销。

## 5. 状态转换

### 5.1 编辑和重新检查

1. 用户在当前成功版本上创建或继续编辑草稿。
2. 客户端按段落保存草稿，并携带草稿修订号。
3. 用户选择“保存草稿并重新检查”。
4. 服务端使用幂等键创建 `queued` 新版本和分析任务。
5. Celery 分析草稿快照，SSE 复用现有任务进度协议。
6. 分析成功后，在一个数据库事务内将新版本标记为成功并更新 `active_version_id`。
7. 新版本的问题全部为未处理；旧版本及其决定保持不变。

分析失败时，新版本标记为失败，活动版本不变，草稿继续可编辑。重复提交相同幂等键返回同一版本。

### 5.2 决定和撤销

单项或批量决定均由服务端事务写入。批量请求中任意一项失败时整批回滚。
撤销要求目标决定仍与操作批次记录的“修改后值”一致；否则返回冲突并要求刷新，禁止覆盖更新后的决定。

### 5.3 版本浏览

默认展示当前成功版本。用户可切换到任意历史成功版本查看原文、问题、决定、预览和历史导出。
历史版本为只读；若要继续编辑，必须从该版本显式创建新草稿和子版本。

## 6. 派生内容与冲突

派生内容服务接收文档版本 ID 和决定快照，按段落生成修改后正文：

1. 仅应用状态为接受且具有最终替换文本的决定；
2. 未处理和已忽略的问题保留原文；
3. 在每个段落内按源字符范围应用替换；
4. 同一字符范围存在多个已接受修改时拒绝生成，并返回冲突问题列表；
5. 结果以文档内容哈希和决定快照哈希缓存。

服务端在接受决定时即检测范围重叠。发生冲突时返回明确的 `409`，界面要求用户保留其中一个，
不自动改变其他决定。

“修改后”视图、差异视图和修改版导出都调用该服务。导出创建时固定决定快照哈希，保证下载内容
不会因后续决定变化而漂移。

## 7. API 边界

具体路径遵循现有 API 命名约定，但必须提供以下能力：

- 列出任务的文档版本和当前版本；
- 获取一个版本的段落、问题、决定和候选建议；
- 创建、读取、更新和放弃编辑草稿；
- 从草稿幂等创建重新分析版本；
- 获取原文、修改后和差异派生视图；
- 提交带版本校验的单项或批量决定；
- 列出操作批次并撤销指定批次；
- 为导出创建不可变的决定快照。

所有写接口使用现有认证和任务访问边界。并发错误使用 `409`，校验错误使用 `422`，找不到或无权访问
不得返回成功形状的空数据。

## 8. 工作台交互

### 8.1 文档区

- 标题区增加紧凑版本选择器和“编辑原文”。
- 文档区提供“原文 / 修改后 / 差异”三段切换。
- 差异视图使用字符级 LCS 表示删除和新增。
- 历史版本显示只读状态和返回当前版本入口。

### 8.2 编辑模式

- 文档区原位切换为按段落编辑器，不进入单独页面。
- 明确显示未保存状态。
- 提供“保存草稿并重新检查”和“放弃草稿”。
- 分析期间展示实时进度；失败后恢复草稿和可执行的重试入口。
- 浏览器离开或切换文件前，对未保存草稿沿用现有脏状态确认模式。

### 8.3 问题检查器

- 展示多个候选建议、来源和说明。
- 用户可选择候选后直接改写，或填写自定义修改。
- 接受操作保存最终文本；忽略不保存替换文本。
- 重叠修改冲突显示涉及的问题并提供跳转。

### 8.4 查找替换

- 审阅模式可以查找当前展示版本，但不显示替换控件。
- 替换只允许在编辑草稿中执行。
- 支持普通或正则搜索、区分大小写、替换当前、全部替换和清除。
- `Enter` 定位下一处，`Shift+Enter` 定位上一处。
- 无效正则在输入位置显示错误并停止执行，不能退化为普通文本搜索。

### 8.5 操作历史

- 批量操作后显示 10 秒快捷撤销提示。
- C2 功能轨道增加紧凑的“历史”入口。
- 历史按时间倒序展示操作类型、影响数量和时间。
- 可撤销批次显示整批撤销动作；发生并发冲突时刷新并说明无法覆盖的原因。

### 8.6 响应式和可访问性

页面继续占满单屏，浏览器页面本身不出现整体滚动条，各功能区独立滚动。
桌面保留四区布局，平板和手机沿用现有底部导航。新增控件必须具备键盘焦点、可访问名称、
状态提示和焦点恢复。定位问题后问题检查器保持可见。

## 9. 错误与恢复

- 草稿修订冲突：保留本地输入，展示服务器最新版本和冲突选择，不自动覆盖。
- 重新分析失败：保持旧活动版本，保留草稿，显示失败原因和重试。
- SSE 断线：按现有重连机制恢复；旧请求代次不得覆盖新版本状态。
- 决定或撤销冲突：刷新相关决定，保留用户意图并明确要求重新确认。
- 派生内容冲突：阻止预览和导出，列出重叠问题。
- 网络失败：禁止显示成功状态，允许使用同一幂等键安全重试。

## 10. 测试与验收

### 10.1 领域单元测试

- 成功版本不可变，活动版本只能指向成功版本；
- 草稿修订号和内容哈希正确工作；
- 单候选兼容、多候选选择和自定义文本；
- 重叠范围检测；
- 操作批次正向和反向变换；
- 字符级 LCS 和派生内容确定性。

### 10.2 API 与数据库集成测试

- 重新检查幂等；
- 分析成功后原子切版；
- 分析失败保留旧版本和草稿；
- 单项和批量决定乐观锁；
- 批量事务回滚；
- 10 秒快捷撤销与长期历史撤销使用同一后端能力；
- 历史版本只读且仍可复现决定和预览。

### 10.3 任务链测试

- 重新分析复用 SSE 进度；
- 断线恢复后终态正确；
- 旧任务回调不能覆盖较新的活动版本；
- 重试不会重复创建版本。

### 10.4 前端与浏览器测试

- 原文、修改后和差异切换；
- 按段落编辑、脏状态保护、保存、放弃和失败恢复；
- 候选选择、候选编辑和自定义修改；
- 正则、大小写、替换当前、全部替换、清除和键盘导航；
- 单项恢复、10 秒批量撤销和历史整批撤销；
- 1280 桌面、平板和手机断点无页面整体滚动；
- 按钮对齐、问题定位后检查器可见和焦点恢复。

### 10.5 一致性验收

在同一决定快照下，“修改后”视图的规范化文本必须与下载文件提取出的正文一致。
重新检查必须产生新版本；旧版本的问题、决定、操作历史和历史导出仍可复现。

功能矩阵中，参考项目审阅闭环的每项生产功能必须标记为“等价实现”或“由更强机制替代”，
不得无说明遗漏。

## 11. 迁移与兼容

现有任务迁移为修订号 1 的成功版本。现有问题和决定关联到该版本；现有单一建议转换为首个候选。
迁移不得重新分析历史文件，也不得改变现有决定语义。

部署顺序为数据库向后兼容迁移、后端双读兼容、前端切换、旧字段清理。旧字段清理必须在新路径
稳定并完成回滚窗口后另行执行，不包含在首次上线中。

本子项目完成后，后续规则、格式和智能复核能力只需生产标准化问题、候选和版本，不应绕过本设计
另建审阅状态。
